# 近期问题复盘与两项任务的交付门禁

日期：2026-10-21。范围：新 Companion 开发者后台及资源流程；蚂蚁、素材采集器暂停新增实施与验收，保留已有提交。

当前结果：后台普通业务仍被 DRAINING 拒绝；资源生成完整链路没有跑通。已完成的 UI、测试和候选补丁不能抵消这个事实。最严重的影响发生在本次维护：03:22:07 UTC前宿主仍OPEN，维护失败后同一进程变为DRAINING，普通业务被拒绝。执行前没有验证失败恢复路径，这是本次应承担的执行决策失误。

以下“事实”有留存记录支撑，“判断”是对执行决策的复盘，不推断操作者动机。

已先读取[10月18日知识库复盘](knowledge-retrospective-20261018.md)、[10月17日恢复记录](next-recovery-20261017.md)、[10月20日收尾](parallel-closeout-20261020.md)。10月18日已经提出“固定用户入口的最小闭环、停止扩大外围验收”；本次没有把这条结论落实为执行门禁，导致同类问题继续出现。

## 1. 版本报告与用户实际看到的版本不一致

**事实。** 曾把部署 d1eae8f / 1.3.173.196、文档 .197 等内部检查点用于交付报告；用户页面实际显示 1.3.173。后续查明 package.json.version 决定前端产品版本，四段 VERSION 是内部 Git 记录，宿主接口没有提供可信的后端产品版本。没有证据支持直接归因浏览器缓存，也没有找到用户记忆中前后端双数字的完整旧实现。

**决策失误。** 没有先区分产品版本、源码提交、构建源、文档提交和实际服务产物，就使用“已部署版本”这一模糊说法。这使用户难以判断拿到的究竟是什么。

**修复与验收。** 页面、关于和复制信息统一标注前端 1.3.173、后端“当前接口未提供”，已部署并核过实际文件。以后交付同时列“产品版本、构建源码 SHA、部署文件 SHA、现场可访问性”；文档提交不改变已部署产物身份。参见[版本来源修正](version-semantics-20261021.md)。

**开工闸门。** 版本来源未确定时写“未知”，不能拿 Node、Bridge 协议、旧 package 或内部 W 代替后端产品版本；缺少 served 文件证据只能称候选构建。

## 2. 测试数量和局部成功替代了真实闭环

**事实。** UI 的假 provider、请求拦截及隔离测试证明了特定逻辑，但真实问答、同步、模型生成等并未执行。蚂蚁 JSON 已有隔离测试及 Creator 导入编译；短 Profiler 回执却 sampleCount=0、未见目标关卡资源，不能证明真实游戏刷新读取了新配置。既有96变体真实导入、PNG/meta/UUID、场景及 Preview/Build/Smoke 的历史证据仍有效，但它们不证明本次新生成链路已完成。

**判断及决策失误。** 分阶段报告虽有部分限制说明，主结论没有始终围绕用户最终操作组织；“又通过若干项”容易给人持续接近完成的印象。10月18日已经指出这个问题，本次仍未形成可执行的完成定义。

**修复与验收。** 每条证据固定标成“代码/隔离模拟/真实组件/真实用户入口”之一。完整资源流程必须是同一隔离工程、同一规范版本、同一输入及同一任务，依次拿到保存读回、真实生成、预览及导出回执。离线导入可以单独验收，名称必须是离线导入，不能标模型生成。

**开工闸门。** 开始前写明入口、测试数据、实际依赖、产物路径和成功条件。没有目标资源加载/结果回读证据，PASS 字段与零错误均不足以提升为业务通过。旧证据仅在输入与实现一致时按原范围复用。

## 3. UI 没有稳定围绕旧交互和主要操作收敛

**事实。** 用户先后指出工程排序与折叠、看板顺序变化、状态不明显、知识库三个子页样式不统一、列表结果跨块显示、问答步骤繁琐、AI图标文字过多以及关于页复制控件冗余。部分页面后来已作批准范围内的精简和统一；这不表示新旧全功能、全状态都已真实验收。

**判断及决策失误。** 实施优先展示“已有接口和保护说明”，对用户当前要完成的主操作、旧后台习惯及信息优先级核对不足。多个位置各自解释状态，增加了阅读成本，也增加来源不一致的机会。

**修复与验收。** 以实际旧路由和操作为功能基线；同一服务只用同一状态来源，加载、未知、失败和未连接分别展示。页面优先呈现当前工程、核心输入、主按钮、结果和短错误；诊断按需展开，不能通过删功能换取简洁。现有批准修复及边界见[UI交付](ui-refinement-20261021.md)、[模型与资源页交付](model-art-ui-20261021.md)。

**开工闸门。** 先列旧操作→新入口→结果反馈的矩阵。候选必须查看正常、加载、失败、未知及窄屏状态；没有逐项证据的功能标未验证，不能把占位或状态标签当功能完成。

## 4. 截图发送占用了主线注意力

**事实。** 对话多次围绕截图生成、上传授权和 Library 403 往返；用户已明确允许“不能发就说明”，后来取消上传。现有记录不足以精确统计浪费分钟数、成功上传数或所有尝试次数，不能编造这些数字。

**判断及决策失误。** 附件交付没有及时与实现主线解耦。连接403已有明确阻塞时，继续讨论上传路径不会推进后台和资源链路。

**修复与验收。** 截图可以留在本地作为视觉证据；发送失败单独说明。用户取消后不再上传或调查403。本轮没有上传截图，已有候选图明确标注隔离模拟。

**开工闸门。** 附件连接拒绝只在有明确恢复证据或新合法路径时再处理；截图成功不作为功能完成或继续开发的前提。不得换通道绕过拒绝。

## 5. 维护前缺少可恢复性预检，导致正常后台被关闭准入

**事实。** `approved-restart-before.json` 记录03:22:07 UTC宿主为 OPEN，当前任务计数均零，但 nativeEpochUnproven=2，unknown 为 NATIVE_PRIOR_EPOCH_UNVERIFIED。随后为加载批准的离线绑定执行官方 restart，停止失败；宿主恢复准入复用了严格停机 idle 判断，历史两条未决使服务持续 DRAINING。随后官方生命周期验证返回 UNKNOWN_CONTEXT_COVERAGE，没有新增退出证明。

**决策失误。** 重启前已经知道两条历史未决。应先核查“停止会怎样拒绝、失败是否能恢复业务、当前产物是否能重建和回滚”，再决定是否进入维护。用户批准一次重启不免除这项技术预检。这次把本来可用的服务推进了无法在现有许可内恢复的状态。

**修复与验收。** 只在隔离副本增加独立的失败准入恢复判断，18/18真实类测试和独立复审通过；严格停机、身份、generation和退出证明保持，历史记录不删。候选未应用，现场未恢复。参见[恢复证据与限制](companion-drain-recovery-20261021.md)。

**开工闸门。** 维护前必须取得只读身份/计数/历史状态、匹配构建及回滚产物，并验证失败后恢复路径；出现不可解释的UNKNOWN或没有允许的恢复方式时，停止维护派发，先交付精确维护方案。操作超时后先核对结果，不能盲重发。

## 6. 安装产物缺少可证明匹配的完整源码版本

**事实。** 安装 source map 有85个项目源，但缺 `src/companion-mcp.ts`、`src/companion/tool-profiles.ts`、`src/companion/types.ts`，完整daemon构建失败。map路径指向旧临时工作树；归一换行后，其记录提交 dacb89b 为74/85匹配（原字节精确匹配仅6/85），当前 main 6ff44f5 为54/85，已知修复提交2994d14为56/85。没有一个已核对的提交能证明是完整安装源码；这不是穷尽全部Git历史或证明源码永久丢失。未用脏工作区、其他版本或占位模块拼接。

**判断及决策失误。** 产物、临时补丁、源码提交和内部版本的关系没有在维护前收齐。隔离修复可审查，却不能据此保证完整重打包或安全替换正在运行的宿主。

**修复与验收。** 保留精确安装SHA、map、最小补丁、缺失模块和三次有界比对结果，停止扩大重建搜索。完整构建失败与18项类测试通过分别报告。

**开工闸门。** 共享宿主维护需先取得对应源码快照或可验证的正式包清单，能完整构建并绑定资源及依赖；没有来源证据不得混版本补齐。新发布产物要保留源码提交、构建输入、依赖及文件SHA、回滚包。

## 7. 并行任务的收尾和主线反馈拖延

**事实。** 对话中父线程多次要求立即报告启动命令、当前阻塞及已经完成的结果，并明确“不必等全面验收”“不要回答问题后停滞”。与此同时，启动、版本、知识库、资源UI、蚂蚁、采集器、适配器维护等多条工作同时推进，部分代码完成但未形成可用主流程。

**判断及决策失误。** 并行分工没有稳定服从唯一的当前交付目标；独立子项完成后，主线程未始终及时收拢结论、分开交付和设置停损点。新的问题又不断叠到旧任务上，增加用户反复推动的成本。没有证据据此认定环境断连是所有延迟的唯一原因。

**修复与验收。** 当前只保留两项：本复盘和资源流。蚂蚁、采集器暂停新增实施与验收；已有提交保留。复盘可独立交付，资源流按一个明确隔离对象串联，不等待所有支线完成才反馈。

**开工闸门。** 每个并行任务只有一个产物、文件单写者和结束条件；根线程负责整合。遇到真实阻塞立即给“已完成/未完成/精确缺口/下一步负责人”，不能用持续研究替代结论，也不因回答新问题丢掉主任务。

## 现在两项任务的完成定义

|任务|本轮应交付|不能称为完成的情况|
|---|---|---|
|近期复盘|本MD、可追溯事实、决策失误、具体修复与开工门禁，独立审查并本地Git记录|只有道歉、原则或没有证据的归因|
|资源生成流|先恢复可靠服务；同一隔离工程完成规范创建保存读回→输入→实际生成→预览→保存导出并回读文件|只通过UI模拟、只导入现成PNG、只恢复服务或仍待模型许可|
